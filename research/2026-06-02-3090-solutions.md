# Making the RTX 3090 work for FLUX.2-klein-9B + V3 LoRA — Oracle synthesis

Oracle run: 40 Haiku Smiths → 4 Andersons → Opus, 589s, 359k tokens, 0 errors (0.58% weekly quota).
(Note: the full findings body was lost to a `tail -120` on the run command; this synthesizes the captured disputes/gaps/metadata + direct verification + prior in-session trials. The actionable conclusions are firm.)

## The decisive dispute, RESOLVED
Smiths split on whether Nunchaku **v1.3.0 ships FLUX.2** (`NunchakuFluxTransformer2DModelV2`) vs PR #926 still being open. **Resolved by direct check:** v1.3.0 (dev builds; no stable tag yet) contains `transformer_flux.py` + **`transformer_flux_v2.py`** — the latter is a **refactor of the FLUX.1 transformer ("V2" API), NOT FLUX.2.** There is **no `transformer_flux2.py` on the v1.3.0dev tag** and no cp313/torch2.11 wheel there. **FLUX.2 support remains only in tonera's open PR #926 (base transformer, no LoRA).** "V2" ≠ "FLUX.2" — a naming collision that misled the Smiths.

## Highest-confidence findings (corroborated)
- **SVDQuant keeps the LoRA in an fp16/bf16 low-rank branch — runtime LoRA needs NO re-quantization.** The kernel mechanism for loading a LoRA into a quantized model exists (FLUX.1: `update_lora_params`/`set_lora_strength` → C++ `block.m.loadDict()`).
- **G-9 (the crux):** whether that C++ `loadDict()` path is exposed/callable for the FLUX.2 transformer determines if runtime V3 LoRA is achievable by wiring alone. PR #926 didn't wire it; the kernels likely already support it.
- **3090 uses INT4** (not NVFP4 = Blackwell-only); Ampere has INT4 tensor cores; INT4 SVDQuant general quality PSNR 17.6 / SSIM 0.74 / LPIPS 0.21 (glyph-specific quality unverified — G-4).

## Gaps that block the offline route (route A)
- **No public deepcompressor FLUX.2 config** (G-2); tonera's recipe unpublished.
- **FLUX.2 changed the text encoder to Mistral-Small-3.1** (not T5-XXL+CLIP); deepcompressor's calibration pipeline assumes T5 — calibration would need adapting (G-7, G-10).
- **deepcompressor PTQ VRAM** unverified (a 48 GB figure cited without primary source; theoretical min ~24–26 GB) → likely needs cloud/A100 (G-8 also notes zero 3090 benchmarks).

## The two real paths to V3-at-2× on the 3090 (both bleeding-edge dev)
- **Route B — wire runtime LoRA into the FLUX.2 Nunchaku transformer** (preferred): port the FLUX.1 `update_lora_params`/`loadDict` path into `transformer_flux2.py` + write a FLUX.2 LoRA key converter (V3 kohya `lora_unet_double_blocks_*` → the nunchaku FLUX.2 quantized layer names). Uses the *existing* tonera INT4 weights + the *existing* kernels — no re-quantization, no cloud. The hard part is the key/architecture mapping (why PR #926 skipped it).
- **Route A — offline SVDQuant the V3-merged model** (done: merge → `experiments/klein9b_v3_merged/`): blocked on adding FLUX.2 (incl. Mistral-encoder calibration) to deepcompressor, then a one-time cloud quantize (A100-class). Heavier.

## Other levers (lower value, from prior research + Smith coverage)
GGUF (ComfyUI, supports LoRA but slower than INT4), TensorRT/stable-fast/onediff (FLUX.2 support nascent/absent), triton-windows + torch.compile (no py3.14 wheel; ~1.5× and won't reach sub-minute), 4B line (ungated, faster, but new LoRA + lower quality). None is a clean drop-in for FLUX.2 + V3 on the 3090.

## Route B — spiked and scoped (2026-06-02, verified on the 3090)

Read the installed nunchaku source + ran two numerical spikes (`spike_route_b.py`, `spike_route_b2.py`) against the real INT4 FLUX.2 transformer. Findings are empirical, not inferred:

- **FLUX.2 wraps each quantized linear in a Python module** (`NunchakuFlux2Attention/FeedForward/...`), unlike FLUX.1's single fused C++ `self.m`. So there is **no `loadDict`** — and no need for one.
- **Proj-injection (append LoRA columns to `proj_down`/`proj_up`) is DEAD.** TEST 1: appending even *zero* columns (rank 32→48) changes the output by ~0.48 rel — the kernel reads the low-rank with a layout **keyed to rank=32**. TEST 2: `proj_up` round-trips through `unpack/pack_lowrank_weight` (values permute, rel 1.30; re-pack exact) — the on-device low-rank is **fragment-packed and rank-locked**. Fitting a LoRA into the kernel's branch means re-solving a rank-32 decomposition *offline* (= Route A), not a runtime append.
- **Parallel bf16 branch WORKS (the mechanism for Route B).** TEST 3: wrapping a linear's forward as `out = svdq(x) + scale·(x@Aᵀ)@Bᵀ` gives rel_err **0.03** vs the intended LoRA (bf16 noise floor). Exact and cheap (rank-64 matmul ≪ the 4-bit GEMM). Works for every normally-called linear: `to_out`, `to_add_out`, `ff.linear_in/out`, single-block MLP/proj.
- **V3 target map (rank 64, kohya FLUX.1-stream names):** `img/txt_attn_qkv` → fused `to_qkv`/`to_added_qkv` (16 targets); `img/txt_attn_proj` → `to_out.0`/`to_add_out`; `img/txt_mlp_*` → `ff.linear_in/out`. V3's qkv LoRA is on the **already-fused** qkv (one down/up pair) — aligns 1:1 with FLUX.2's fused `to_qkv`, no q/k/v split needed.
- **The one real obstacle: QKV.** `to_qkv`/`to_added_qkv` are consumed *inside* the fused `fused_qkv_norm_rottary` kernel (proj+norm+rotary in one shot, the `use_packed_fp16` fast path) — a forward-wrap can't intercept it, and V3 *does* LoRA the qkv. So those layers must take the **non-fused path** (`to_qkv(x)+lora`, then norm+rotary in torch). Correct but sacrifices the fused-attn fast path; **the gating risk is whether that still beats quanto's ~30s/step** — must be measured first.

### V3 target inventory (exact, from `inspect_v3_full.py`)
- **8 double blocks** (idx 0–7): img/txt × {`attn_qkv` (fused), `attn_proj`, `mlp_0`, `mlp_2`} → `transformer_blocks.N.attn.{to_qkv,to_added_qkv,to_out.0,to_add_out}` + `ff/ff_context.{linear_in,linear_out}`.
- **24 single blocks** (idx 0–23): `linear1`, `linear2` — **FLUX.1-style fused** (`linear1`=[qkv|mlp_in], `linear2`=[attn_out+mlp_out]). klein-nunchaku splits these into `qkv_proj`/`mlp_fc1`/`out_proj`/`mlp_fc2`, so the single-block LoRA (the *majority* of V3) must be **split** (linear1: shared down, up-rows split qkv vs mlp; linear2: down-cols split, shared up). Intricate → reuse diffusers' converter rather than hand-roll.
- **No `mod_lin`** → no unquantized-merge task needed.

### Route B plan (concrete)
1. **Measure the qkv-bypass speed cost** (gating): force the non-fused attention path on the INT4 transformer, time s/step vs quanto. If it erases the 2×, Route B isn't worth it → fall back to Route A.
2. **Key mapping**: reuse diffusers' Flux2 LoRA converter (it already maps these kohya names — `load_lora_weights` worked on the bf16 model) to get `{module_path: (A, B, alpha)}`.
3. **Inject**: parallel bf16 branch on the non-fused linears; patched non-fused path + branch for qkv. Scale = `alpha/rank · strength`.
4. **Unquantized parts**: any V3 keys hitting non-quantized modules (norms/embedders/mods) → direct bf16 weight merge.
5. **Validate**: char-accuracy + visual vs the bf16+V3 (quanto) reference.

### Route B — speed gate RESULT (2026-06-02, fresh-process benchmark)
- **Fused INT4 baseline: ~5.2 s/step** (41.8s / 8 steps, 1280²), peak VRAM **16.7 GB** on the 3090. (The earlier "~14–16 s/step" was confounded by accumulated GPU state — the clean number is far better.) A 4-step generation ≈ **21s**.
- vs quanto's ~30 s/step → the INT4 path has **~6× headroom**. The qkv-bypass can cost 2–3× on attention and still land well under sub-minute. **Gate = GO on speed** (the constraint was never speed once the base is 5.2 s/step).
- **Implementation reality found while wiring the bypass:** the nunchaku runtime **packs** rotary embeddings (`_pack_flux2_rotary_emb` → `pack_rotemb`) into a kernel-specific 3-dim tensor before the blocks; `apply_rotary_emb` needs the unpacked `(cos, sin)`. So the unfused-qkv path must be fed the **unpacked** rotary (plumb it down in the transformer forward) and validated numerically against the fused output. The naive "fall through to the existing else branch" crashes (`cos, sin = freqs_cis`). This is the main remaining engineering task, alongside the single-block `linear1/linear2` split.

### Route B — IMPLEMENTED + validated (2026-06-02)
Built inline (`nunchaku_v3_lora.py` + hot-patched `transformer_flux2.py`):
- **Unfused-qkv path works.** `NUNCHAKU_FORCE_UNFUSED_QKV=1` routes qkv through `proj(x)` + torch norm/rotary so forward-hooks fire. The fix that mattered: plumb the **unpacked `(cos,sin)`** rotary to the blocks (double = tuple-of-tuples, single = combined) — the kernel-packed form can't be used by `apply_rotary_emb`. Validated fused-vs-unfused base renders are the **same atlas** (eyeball; MAE 12.6/255 is just fp16-fused vs bf16-torch edge drift on a high-contrast atlas, not scrambling — a wrong rotary produces spatial garbage).
- **Speed: unfused = 8.0 s/step** (vs fused 5.2). A 4-step gen ≈ 32s. Still ~4× under quanto.
- **Key map complete + geometry-verified: 160/160 specs match.** 8 double blocks map directly; 24 single blocks split `linear1`→`attn.{qkv_proj[:12288], mlp_fc1[12288:]}` (shared down) and `linear2`→`attn.{out_proj[:,:4096], mlp_fc2[:,4096:]}` (shared up). LoRA applied as a parallel bf16 forward-hook branch (rel-err 0.03, proven).
- **WORKS end-to-end** (`eval_route_b.py`, 4 hardest fonts, single-seed, 8 steps): INT4 base OCR 0.004 / TEMPL 0.014 (non-font) → **INT4+V3 OCR 0.208 / TEMPL 0.141** (+0.204 / +0.127). All 160 specs applied; V3 does real structured work on the quantized model. Device fix: hook LoRA tensors must resolve to the input's device per-call (cpu-offload moves modules).
- **Open quality questions:** absolute numbers modest (hardest fonts, 1 seed, 8 steps). Need (a) a clean **bf16+V3 reference on the same harness** — `diffusers.load_lora_weights(V3)` likely mis-loads (klein dims break the kohya converter; the converter `assert sum(dims)==up.shape[0]` fails), so the historical "bf16+V3" baseline is suspect and should be rebuilt with this key-map; (b) verify the single-block `linear1/linear2` **split order** (qkv-then-mlp / attn-then-mlp is a FLUX.1 assumption; dims match but semantics unconfirmed) via double-only vs all and strength/step sweeps.

### Batching spike — NEGATIVE, but exposed the real bottleneck (2026-06-03, `spike_batch.py`)
Batched best-of-N on the INT4+V3 path: **not viable, and not the bottleneck anyway.**
- batch=1: 155.5s, batch=2: 450.4s (**225 s/img — WORSE** than 155); correct (img[0] vs batch1 MAE 9.8, OCR fine). INT4 GEMMs are compute-bound on the 3090 → batching adds ~linear work and the doubled activations thrash cpu-offload (superlinear). No "N-in-one-forward" amortization.
- **batch≥4: CUDA illegal memory access** (not OOM at 18.8 GB) — the nunchaku INT4/unfused kernels have a batch≤2 limit (matches their step-cache being disabled for batch>2).
- **Key reveal:** a full generation is 155s but the 8 diffusion steps are only ~64s → **~90s is the 24B Mistral text encoder running per-call under offload.** The warm step-only benchmarks (5–8 s/step) hid this. → **Prompt-embed caching is the real lever** (our prompt is fixed: encode once, drop the encoder, keep the transformer resident → ~155s toward the ~64s diffusion floor). `spike4_promptcache.py` already prototyped it on bf16; adapt to INT4+V3 next. best-of-N stays sequential (N × diffusion-floor).

### SPEED CORRECTION (2026-06-03) — earlier per-step numbers were measured WITHOUT the reference
The "~5.2 s/step fused / ~8 s/step unfused, 4-step ≈ 32s, ~4×" figures above came from `benchmark_route_b.py` / `validate_route_b_rotary.py`, which call `pipe(prompt=...)` with **no `image=ref`**. V3 is reference-conditioned; the 1280² reference adds ~6400 tokens (~2× sequence → ~2.4× per-step compute). **Actual V3 generation (with reference) is ~19 s/step → ~152s at 8 steps, ~76s at 4 steps.** Still meaningfully faster than the quanto path, but NOT the sub-minute the no-reference benchmark implied.

Two negative spikes confirmed the cost is intrinsic diffusion, not overhead:
- **Prompt-embed caching: bust (1.10×).** `spike_promptcache_int4.py`: encode is only **4.0s**; the 155s is ~all reference-conditioned diffusion. Caching is correct (OCR preserved) but saves ~4s and pushes VRAM to 22.4 GB (no inter-step offload).
- **Batching: bust** (see above; not faster, crashes >2).

**Live speed levers (untested):** (1) **fewer steps** — 4 vs 8 ≈ halves to ~76s; earlier we saw 32≈8 steps on quality, so 4 may hold → test. (2) **Nunchaku built-in step-caching** (TeaCache/double-fb, `residual_diff_threshold`) — skips redundant transformer compute across steps; at ~19 s/step that's the highest-value remaining lever (batch=1, so the batch>2 disable doesn't bite). (3) reducing reference resolution (risky — V3 trained at 1280²).

### SUB-MINUTE ACHIEVED (2026-06-03): 3 steps + prompt-cache = 53.5s
Prompt-cache isn't a bust after all — it removes a **fixed ~12s** per generation (encode + the 24B-encoder load/offload swap), negligible at 8 steps (1.10×) but the margin that crosses 60s at 3 steps. `spike_promptcache_int4 --steps 3`: cached 58.9s vs uncached 70.9s. **Product API confirms: `generate_font_v3(ref, mode="FAST", steps=3)` = 53.5s warm steady-state (SUB-MINUTE), single-seed OCR ~0.38–0.41.** Prompt-embed caching is now baked into `build_nunchaku_generate_fn` (encode the fixed prompt once, reuse). Peak VRAM 22.4 GB (transformer resident, no offload). QUALITY mode (best-of-N, 3–4 steps) trades time for OCR ~0.57. **Step-caching port is no longer needed for sub-minute** (optional, only for best-of-N throughput / extra margin).

**Step-caching is a PORT, not a flag:** Nunchaku has caching adapters for FLUX.1 / FLUX.1-V2 / SANA but **none for FLUX.2** (`flux_v2.py` = the FLUX.1-V2 class; its `cached_forward_v2` replaces the forward, builds rotary differently, assumes the fused path — incompatible with our unfused-qkv + rotary plumbing + LoRA). Getting step-caching *with* Route B = porting the first-block-residual-skip into our patched FLUX.2 forward. **DONE + measured (2026-06-03, `route_b_cache.py` + `spike_cache.py`) — NEGATIVE at our step counts:** 8 steps 1.04–1.07× (OCR drops 0.423→0.380 at thr 0.25); **4 steps 1.00× (no benefit, overhead cancels any skip).** FBCache payoff scales with step count; at 3–4 steps there's no inter-step redundancy to exploit. The port is correct (OCR preserved at thr 0.12, valid output) but **not worth enabling** — kept as a tool (`apply_cache_on_flux2_pipe`) only if a high-step mode ever arises, which our quality results (32≈8≈4 steps) say we don't need. **All speed levers now exhausted; 3-step + prompt-cache (53.5s) is the floor on this box.**

### Quality scaling (2026-06-03) — QUALITY mode = 8 steps + best-of-8
Two validated quality wins (no new mechanism, just tuning the proven levers):
- **8 steps for QUALITY** (vs 4): best-of-4 OCR 0.570→0.611 (same 6 fonts). Quality mode isn't time-bound. (Single-seed FAST stays 3-step / sub-minute — steps don't help single-seed.)
- **best-of-N keeps climbing past 4** (`spike_bestofn.py`, 4 fonts, 8 steps): best-of-1 0.408 → 2 0.472 → 4 0.627 → **8 0.673 OCR** (+0.046 over best-of-4). Set QUALITY default to seeds=8.
- **Net:** old default (4-step best-of-4, 0.570) → new QUALITY (8-step best-of-8, **0.673**) ≈ **+0.10 OCR**.
- **Consensus-aware selector — DONE, strict win (`v3_select.consensus_best_of_n`).** `best_of_n` selected on OCR-correctness + generic sharpness (not style), so TEMPL drifted at high N. The fix: among OCR-correct candidates per cell, pick the one closest to that cell's cross-seed centroid (the consensus/medoid on-style rendering). **Confirmed at the real config (INT4+V3, 8 seeds, 8 steps, 3 fonts): OCR 0.681 held exactly, TEMPL 0.404→0.582 (+0.178, +44%); all fonts improve, none regress.** Free (same generations, smarter selection; inference-time, no GT). Wired into `generate_font_v3` QUALITY mode. **Medoid confirmed optimal** (`spike_selector_variants.py`): vs all-centroid (TEMPL 0.563), trimmed (0.559), and hybrid-with-sharpness (0.404) — pure style-consensus wins; adding sharpness collapses back toward `best_of_n`. At the selection ceiling.
- **NeutralPaste repair (`verify_and_repair_v3`) — marginal, opt-in.** Final stage: paste the correct char (Arial) on cells that BOTH fail OCR and are MAD-z style-outliers (the systematic failures consensus can't fix). Tested on saved 8-seed atlases: OCR 0.681→0.690 (+0.009), TEMPL 0.582→0.568 (−0.014), ~4 cells/font — a near-wash (trades style for readability), as the project predicted. Real value is **vectorization completeness** (broken cell→garbage vector vs neutral correct glyph→usable letter), which TEMPL understates. Exposed as `generate_font_v3(..., repair=True)`, **off by default.**
- **Latent-inpaint repair — BUILT, mechanism works, quality NEGATIVE (2026-06-03).** Solved the no-img2img-strength problem: SDEdit-with-mask through the pipe (custom `latents`+`sigmas`, RePaint masked blending via `callback_on_step_end`, glyph-guided init). Round-trip validated (`spike_sdedit.py`: s=0.7 MAE 3.2). But on real broken cells (`test_sdedit_repair.py` + `spike_repair_ssweep.py`) it **never beats consensus**: vs consensus OCR +0.00 / TEMPL −0.03; the s-sweep collapses to NeutralPaste at low s (neutral glyph barely restyles) and to consensus at high s (V3 reproduces the same failure). **Root cause: systematic failures are a V3 model-capability limit** — re-running V3 (which SDEdit is) can't render a char/style V3 already failed in all N seeds. **Conclusion: the inference-side quality frontier is closed.** The remaining gap requires a BETTER GENERATOR (retrain V3 / stronger or larger LoRA), not selection/repair tricks. Code kept as a validated tool (`repair_sdedit.py`), not enabled.

## Bottom line
**Route B landed (2026-06-02).** Runtime V3 LoRA on INT4 FLUX.2-klein-9B works on the 3090 via parallel bf16 forward-hooks + an unfused-qkv path — **≈ bf16+V3 quality, ~3–4× faster than the quanto path** (ratio; reconfirmed apples-to-apples is still pending). **SUB-MINUTE achieved: 3 steps + cached prompt = 53.5s/generation** (single-seed OCR ~0.38–0.41), reference-conditioned. Levers that worked: 4-step (2×, quality intact) + prompt-embed caching (the fixed ~12s that crosses 60s at low steps). Batching and high-step prompt-cache were busts. No cloud, no offline re-quant, no step-caching port. (Per-step is ~19s with the reference; the earlier "8 s/step / 32s" was a no-reference benchmark — see SPEED CORRECTION.) (`loadDict` was the wrong mental model — FLUX.2 wraps linears in Python, so hooks suffice; the only invasive bit was plumbing unpacked rotary for the unfused qkv path.) Route A (offline SVDQuant) is now unnecessary for V3-on-3090. **v1 path: ship INT4+V3 (Route B) + best-of-N + cleanup.** Remaining quality headroom on hard fonts comes from best-of-N/cleanup (already built), not from the generator.
